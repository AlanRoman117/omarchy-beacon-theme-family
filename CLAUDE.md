# CLAUDE.md

Context for working on this repository. Read this before changing anything.

## What this is

**Beacon** is a family of six themes for **Omarchy 4 "Quattro"** (Arch + Hyprland
+ a Quickshell/QML desktop shell). A dark and a light default, plus red-green
safe and blue-yellow safe variants of each.

The palettes are **generated, not hand-picked**. Colours are solved for contrast
targets and verified against WCAG 2.2, APCA, and simulated colour vision
deficiency before release.

## Scope boundary — do not cross this

Beacon helps people with **low vision** and **colour vision deficiency**. It does
**not** make Omarchy usable with a screen reader, and nothing in this repo should
imply that it does.

Screen reader support is blocked below the theme layer: Omarchy ships no
accessibility bus (`at-spi2-core`, `orca`, `speech-dispatcher` are all absent
from the package manifests), Hyprland has no AT-SPI story, and the GPU terminals
Omarchy ships do not expose text to assistive technology. A palette cannot fix
any of that.

If asked to add screen reader claims, push back. Over-claiming here misleads
exactly the people who most need accurate information.

## The golden rule

**Never hand-edit these files. They are generated.**

| Generated file | Generated by |
|---|---|
| `themes/*/colors.toml` | `tools/verify.py` |
| `themes/*/vscode-theme.json` | `tools/verify.py` (built by `tools/vscode.py`) |
| `vscode-extension/` | `tools/vscode_extension.py` |
| `themes/*/shell.*.toml` | `tools/assets.py` |
| `themes/*/backgrounds/README.md` | `tools/assets.py` |
| `themes/*/README.md` | `tools/theme_readmes.py` |
| `themes/*/preview.png`, `cvd-proof.png` | `tools/preview.py` |
| `CONTRAST-REPORT.md` | `tools/verify.py` |

To change a palette, edit the `VARIANTS` dict in `tools/verify.py` and re-run.
The per-theme READMEs read their numbers out of the live palette objects, so a
published README cannot drift from the colours it documents. Hand-editing breaks
that guarantee silently.

Full regeneration:

```bash
python3 tools/verify.py         # palettes + VS Code themes + CONTRAST-REPORT.md
python3 tools/assets.py         # shell overrides + background prompts
python3 tools/theme_readmes.py  # per-theme READMEs
python3 tools/preview.py        # preview.png + cvd-proof.png
python3 tools/vscode_extension.py  # VS Code extension package
```

Hand-maintained: root `README.md`, this file, `publish.sh`, `LICENSE`,
`tools/omarchy-hooks/beacon-vscode.sh`, and the
actual wallpaper images.

## How the generator works

The hard problem is not hitting 7:1. It is hitting 7:1 **and** keeping six
colours apart, because those fight. Raising contrast means compressing toward
one end of the lightness axis, which is also what collapses hues. A greyscale
theme passes AAA perfectly and is useless.

1. **Hues are fixed per variant** in `VARIANTS[name]["hues"]` as `(hue, chroma)`
   in Oklch. Red-green variants use Okabe-Ito style substitutions: red at hue 38
   (vermilion, not crimson), green at hue 172 (bluish-green, not grass).
2. **Lightness is assigned by brute force.** A fixed contrast ladder is
   distributed across the six hues by trying all 720 permutations and keeping
   the one that maximises minimum perceptual distance under simulation.
   Lightness is the only channel a dichromat keeps, so **the ladder is the
   separation mechanism**, not a by-product.
3. **Each colour's lightness is solved by binary search** to land on its target
   exactly. Compliance is true by construction.

### Invariants that must not regress

- **Nothing below 7:1** against its background. Includes `muted` (comments,
  ANSI `color8`), all six chromatic slots, and all six bright slots.
- **Chroma floor** (`CHROMA_FLOOR`): rejects any assignment that gamut-crushes a
  slot. Without it "green" resolves to white on dark and "cyan" to black on
  light. If you widen the ladder, this is what stops the palette degenerating.
- **Plausibility rule** (`plausible()`): yellow is never the darkest thing on
  screen, red is never the palest, in either mode.
- **Priority pairs** (`PRIORITY_PAIRS`) are weighted above the other nine
  combinations: red/green, red/yellow, green/cyan, red/blue, yellow/green.
  These are the ones that cost something when confused (`git diff`, test
  pass-fail, error vs warning).
- **Dark variants are cross-checked with APCA.** WCAG 2.x overstates contrast
  when both colours are dark, so a dark pair can pass 7:1 and still read badly.
- **`orange` never moves the six slots.** It is solved in `solve_orange()`
  *after* the 720-permutation search, picking the contrast target that keeps
  it furthest from its nearest slot. Do not add it to `SLOTS`: that changes the
  optimisation and every verified number with it.
- **The VS Code theme gates the build.** `vscode.build()` returns every
  text/surface pair it creates, and `verify.py` raises and writes nothing if a
  required one fails: 7:1 resting text, 4.5:1 text on highlights, 3:1
  non-text. If you add a colour key there, add its check too.

### VS Code theme design

- **Resting surfaces step away from the text.** Chrome and widgets are darker
  than `background` on dark themes and lighter on light ones. `background` is
  then always the restrictive surface, so anything solved against the editor
  holds everywhere else. Do not make the side bar lighter on a dark theme.
- **Highlights are solved against the weakest text colour**, then written as
  translucent overlays (`overlay()`) so VS Code can layer decorations under
  them. The check composites them over `background`.
- **Use `muted` only as text.** Omarchy's generic template also uses it as a
  fill and a border, which is the main reason Beacon looked broken in VS Code.
  Borders use their own 3.3:1 neutral, and dividers a decorative 1.6:1 one.
- Faded unused code is disabled (`editorUnnecessaryCode.opacity` is opaque)
  and marked with a dotted underline instead, because fading breaks AAA.

### Tuning gotcha

Widening the contrast ladder helps light variants and **hurts** dark ones. On a
dark background, pushing past roughly 16:1 saturates toward white and collapses
chroma differences, shrinking perceptual distance. Current ladders were chosen
empirically:

```python
DARK_LADDER  = [7.2, 8.8, 10.4, 12.0, 13.6, 15.2]
LIGHT_LADDER = [7.0, 8.2,  9.4, 10.6, 11.8, 13.0]
```

The default variants optimise for `("normal",)` only. Optimising them for all
four vision types produced visibly worse hue identity for no benefit — the CVD
variants exist to do that job.

## Documented exceptions

Three places deliberately miss a threshold. All are in the READMEs. Do not
"fix" them without reading why.

**Selection band, ~2.5:1 against the desktop** (1.4.11 asks 3:1). Selected text
holding AAA and the band clearing 3:1 are mathematically incompatible on a
near-black background. Legible text won.

**Light-mode chromatic colours are dark jewel tones.** Clearing 7:1 on a
near-white background requires sitting below about 9% relative luminance. There
is no bright AAA-compliant orange on white. If someone wants brighter light-mode
colours, the honest move is to target AA and say so. On the light variants
`orange` lands as a dark brown for the same reason.

**VS Code highlighted text is AA (4.5:1).** Selection, find matches and diff
highlights have to move toward the text to be visible at all. At 7:1 they
would sit about 1.0:1 against the editor, which means invisible. They land at
about 1.5:1. Resting text stays AAA.

On the Red-Green variants, diff inserted and removed highlights are equally
light, so they differ by hue only. The gutter `+`/`-` markers and the solid
gutter bars (palette red and green, which are separated in lightness) carry
that distinction. This is documented in their READMEs.

## Omarchy platform facts

Verified against the `quattro` branch docs. Re-check before relying on these,
since Omarchy iterates fast.

- `colors.toml` is the master file. Omarchy renders every app config from it via
  templates. Keys: `mode`, `accent`, `selection`, `muted`, the
  `background`/`dark_background`/`darker_background`/`lighter_background` ramp,
  the `foreground`/`dark_foreground`/`light_foreground`/`bright_foreground`
  ramp, named colours, and ANSI `color0`–`color15`. `muted` doubles as `color8`.
- **`omarchy theme install <git-url>` strips code-running files** — any `*.lua`
  (including `hyprland.lua` and `neovim.lua`), terminal configs, `vscode.json`,
  and symlinks at any depth. Colour-only files survive. **Beacon is colour-only
  by design**; keep it that way or themes will silently fall back to generated
  defaults.
- **VS Code:** a stock theme names a marketplace theme in `vscode.json`, which
  a cloned theme cannot ship. Without it Omarchy renders
  `$OMARCHY_PATH/default/themed/vscode-theme.json.tpl` and applies it as the
  local "Omarchy" theme (`omarchy-theme-set-vscode`). A theme that ships its own
  `vscode-theme.json` keeps it: the file survives the install filter, and the
  template step never overwrites a file already staged.
- **Hook ordering:** `omarchy-theme-set` runs `omarchy-theme-set-vscode` inside
  `run_parallel`, which waits for every job, and only then calls
  `omarchy-hook theme-set <slug>`. A `theme-set` hook therefore always sees
  `workbench.colorTheme` already set to "Omarchy". This is what
  `tools/omarchy-hooks/beacon-vscode.sh` relies on to switch VS Code to
  "Beacon Dark" and friends live, when the `beacon-themes` extension is
  installed. A theme cannot install a hook for the user. Validated live on
  2026-09-14: Beacon-to-Beacon switches apply with no reload.
- **Detect VS Code extensions through `extensions.json`, not folders.** A
  running VS Code leaves an uninstalled extension's folder on disk until it
  restarts. The first version of the hook checked the folder, and after an
  uninstall it named "Beacon Light", a theme that no longer existed. The hook
  now asks the registry with `jq`, with a `grep` fallback.
- **Missing `colors.toml` keys fall back silently.** `omarchy-theme-color`
  substitutes `yellow` for a missing `orange`, among others. Run
  `omarchy-theme-color --file colors.toml --all` to see what templates receive.
- **Section overrides replace the whole section.** A `shell.lock.toml` with
  three keys drops the other nine `[lock]` keys from the template. The shell
  then falls back to palette-derived defaults in
  `$OMARCHY_PATH/shell/Commons/Color.qml`, which are unverified. `[lock]` has a
  `background`/`background-alpha` card behind the password field, default 0.8.
- **One theme per repository.** Omarchy expects `colors.toml` at the repo root,
  which is why `themes/` is published outward via `publish.sh` subtree splits
  rather than installed from this monorepo directly.
- `shell.<section>.toml` files are **section overrides**. Never ship a full
  hand-written `shell.toml` — it replaces the generated file wholesale and would
  silently miss any key a future Omarchy release adds.
- **Border alphas are pinned to `1.0`.** Translucency eats the 3:1 that 1.4.11
  requires of a control boundary, and a focus ring at 60% alpha does not meet
  2.4.13.
- `light.mode` marker file (plus `mode = "light"`) pairs light variants with
  GTK/GNOME light mode.
- **Local testing:** a plain directory or symlink in `~/.config/omarchy/themes/`
  is treated as the user's own theme and stages in full, bypassing the install
  filter. Good for an edit-reload loop, but it will **not** catch a file that
  would be dropped on a real install. Do one real clone-install per theme before
  publishing and watch stderr.

## Wallpapers

Per-variant hue policy, which is not optional:

| Variant | Allowed | Forbidden |
|---|---|---|
| Dark / Light | any, low saturation | — |
| Red-Green | blue, sky blue, navy, orange, amber | green, red, magenta |
| Blue-Yellow | vermilion, green, magenta, amber, cream | blue, teal, cyan |

A red-green gradient is invisible to exactly the people the red-green variant
serves. Same logic inverted for blue-yellow.

Universal constraints: flat papercut style, hard edges, no gradients, no glow or halo, no drop
shadows, no text or lettering, no dot grids or halftones or fine repeating
patterns (visual stress risk, and they shimmer through bar translucency).

Luminance rule, which is what the audit measures:

- Dark themes: central third of the frame free of anything above 20% luminance.
- Light themes: central third free of anything below 50% luminance.

That reserved centre is where lock screen UI lands.

### Current set

Four flat papercut nature scenes per theme, named
`beacon-<variant>-NN-scene-name.jpg`. Each family has its own setting: Dark is
night, Light is morning, Red-Green is ocean and desert, and Blue-Yellow is
forest, flowers and volcano, with no blue sky. All 24 pass the centre rule
(0.00% in the central third), the hue policy, and CVD model divergence (at most
2.44), before and after upscaling.

**Upscaling.** The generator caps at 1792x1008, so every image is upscaled with
Upscayl's command-line engine (`upscayl-bin`, model `digital-art-4x`, scale 4),
then resized with Lanczos to 2560x1440 and saved as JPEG quality 90. That comes
to 36–284 KB per image, 2.2 MB for all 24. Compared on the same image:

- Gemini's upscaler added grain to the flat sky (noise 0.19 to 1.35), lightened
  the darks by 4–6%, and produced 1.7 MB files at an odd 2730x1536.
- Upscayl Digital Art kept skies flat, drifted colour by at most 1.040:1 in any
  region across all 24, and left CVD divergence essentially unchanged. It has
  crisper edges than Upscayl Standard.
- Avoid Remacri, Ultramix and Ultrasharp: they are non-commercial models.
- The upscale nudged the darkest greens in Blue-Yellow Dark 01 and 04 from
  about hue 150 to 155–160, into the edge of the audit's rough teal band
  (1.2–1.5% of pixels). They still read as green, and tritan divergence did
  not move. Not a policy breach, but check it if those images are redone.
- **Hand touch-up (done, 2026-09-14).** The upscaler left faint smudges and
  several colours sharing areas that should be one flat colour. The user
  cleaned all 24 in GIMP, exported at 4:4:4 chroma subsampling. The colours
  covering 98% of each image dropped sharply (for example 124 to 42 on
  Red-Green Dark desert, 25 to 3 on ocean moonrise), and flat-area noise fell
  everywhere. The re-audit still passes: centre third 0.00%, divergence at most
  3.59, largest regional drift 1.075:1, which comes from the cleanup itself.
  The teal-band pixels in Blue-Yellow Dark 01 and 04 fell to 0.8–0.9%.
  **Export edits at 4:4:4:** the default 4:2:0 blurs colour along the edges of
  saturated shapes.

**Papercut, not photographs.** Nature was the user's direction. Realistic
grass, leaves, star fields and water are the fine repeating detail the visual
stress rule forbids, so the style keeps nature to large flat shapes. Allowing
photos means revisiting that rule first, not just the prompts.

The Bauhaus geometric set it replaced is in git history (commit `ed0c0fd` and
earlier). The user did not like it.

Lessons from generating these:

- **Name the sky by what it is not.** "Deep navy sky (#10141A)" produced
  saturated navy, and the generator ignored the hex. That navy alone scored up
  to 7.17 model divergence and failed all four Red-Green Dark images. "Very dark
  desaturated blue-black, almost black; not navy, not royal blue" fixed it
  (0.70–2.44).
- **Forbid a halo explicitly** on suns and moons. "No glow" alone still gave a
  soft light along the horizon.
- **Pin landforms to the bottom fifth or a corner.** Horizons, rising
  diagonals and bands drift through the centre otherwise. The Bauhaus batch
  taught this.
- **Check dark shapes by eye.** Deep green and magenta sit under the 20%
  luminance cutoff, so the numbers pass them even right where the lock screen
  draws.
- **Advisory fine detail at the edges was accepted:** 04 grass blades, 06 bark
  dashes, 21 dense flowers, and 24 thin zigzag terraces. 24 is the closest to a
  repeating-stripe pattern.

Adding a wallpaper means dropping it into `backgrounds/` and re-running
`tools/assets.py`, which lists the directory contents, with scene names taken
from the filenames, in `backgrounds/README.md`.
`cvd-sim/` holds the rendered simulations from `check-wallpaper.py`. It is a
local review aid and is not published.

### Known limitation in `check-wallpaper.py`

`worst_block()` scans **all 144 blocks anywhere in the frame** and gates on the
worst. The lock screen only draws in one region, so a bright mass in a corner is
harmless but still fails the check. On the first real batch this failed 9 of 9
images, including ones that are fine in practice.

**Treat the percentage as the signal and the block contrast as advisory.** Under
about 15% "fighting area" is acceptable with a scrim.

Open improvement: make the audit region-aware — gate on the central band, report
the rest advisory. This is the correct version of the tool and has not been
written yet.

Model divergence is the trustworthy metric and has been clean throughout
(0.29–2.58 against a threshold of 4), meaning Machado and Viénot agree on every
colour used so far.

## Decisions already made

Recorded so they are not relitigated.

- **MIT, not Apache 2.0.** Omarchy is MIT and the whole theme ecosystem follows.
  Apache's patent grant has no work to do on hex values, and its NOTICE
  propagation is friction for something meant to be forked. An MIT file also
  drops cleanly into Omarchy's own `themes/` if a variant is ever upstreamed.
- **Monorepo + subtree split**, not six independent repos. Authoring happens
  once; `publish.sh` pushes outward. Six hand-maintained repos would drift.
- **"Beacon", not "Signal".** 37signals is DHH's company and the origin of
  Omarchy, so a theme called Signal there would read as semi-official.
- **Protanopia and deuteranopia share one variant; tritanopia gets its own.**
  The first two sit on nearly the same confusion axis. They are not identical —
  protanopia has reduced luminance sensitivity to red — so the shared variant is
  tuned for the **protan worst case**. Anything working for protan works for
  deutan; the reverse is not reliable.
- **Blue-Yellow variants deliberately leave red and green close.** Tritanopia
  does not affect that axis. This means they are **not** general-purpose
  colourblind themes and would harm red-green users. That warning appears in
  three places and must stay in all three.

## Testing findings worth keeping

From a Chromium DevTools vision-deficiency sweep of candidate wallpapers:
**reduced contrast was harsher than any colour-blindness filter.** It simulates
low vision and poor displays, which affect far more people than tritanopia does.
Anything that survives reduced contrast and greyscale survives everything else.

That is also the empirical argument for the palette method: lightness separation
survives every filter, hue separation only survives some.

## Dependencies

Colour maths is stdlib. `preview.py` and `check-wallpaper.py` need Pillow only:

```bash
sudo pacman -S python-pillow
```

Do not reintroduce NumPy. It was removed on purpose — Omarchy's Python is
externally managed, so every extra dependency is real friction for a project
whose point is lowering barriers.

## Writing conventions for docs in this repo

- State trade-offs plainly rather than hiding them. The "What is deliberately
  not AAA" section is a feature of the documentation, not an embarrassment.
- Give real numbers, not adjectives.
- Never imply screen reader support.
- Decision guides should ask about lived experience ("have you ever had trouble
  telling red from green") rather than asking people to self-diagnose as protan
  or deutan.
