# Beacon — an Omarchy theme family

Six themes for **Omarchy 4 "Quattro"**: a dark and a light default, plus
red-green safe and blue-yellow safe variants of each.

Every colour in every variant is generated by solving for a contrast target,
not chosen by eye, and machine-verified before release against WCAG 2.2
relative-luminance contrast, APCA Lc, and simulated protanopia, deuteranopia
and tritanopia. The numbers live in [`CONTRAST-REPORT.md`](CONTRAST-REPORT.md)
and you can reproduce all of them with `python3 tools/verify.py`.

**Nothing in any palette drops below the WCAG AAA 7:1 threshold** — including
comment text, all sixteen ANSI slots, and the bright ANSI slots.

## Scope, stated plainly

Beacon improves things for people with **low vision** and **colour vision
deficiency**. It does **not** make Omarchy usable with a screen reader.

That distinction matters enough to put at the top. Screen reader support on
Omarchy is blocked below the theme layer: there is no accessibility bus in the
default install, Hyprland has no AT-SPI story, and the GPU terminals Omarchy
ships do not expose their text to assistive technology. None of that is
something a palette can fix, and a theme that implied otherwise would be
misleading the people who most need accurate information.

What a palette *can* do is guarantee contrast, keep colours distinguishable
without relying on hue discrimination, and make focus unmistakable. That is
what this family does.

## Which one should I use?

Most people do not know whether they are protan or deutan, and do not need to.

1. **Have you ever had trouble telling red from green?** Ripe fruit, status
   lights, `git diff`, a red line on a green chart. If yes, use a **Red-Green**
   variant. This covers roughly 8% of men and 0.5% of women of Northern
   European descent, and it is by far the most likely answer.

2. **Have you ever had trouble telling blue from green, or yellow from pink?**
   If yes, use a **Blue-Yellow** variant. This is rare, around 0.01% of people,
   and unlike red-green deficiency it is not sex-linked, so it affects men and
   women about equally.

3. **Neither?** Use plain **Beacon Dark** or **Beacon Light**. They have the
   widest hue range and the most conventional colours.

4. **Not sure?** Install a Red-Green variant and a default, switch between
   them, and keep whichever makes `git diff` easier to read. That is a better
   test than any self-report.

One warning, because it cuts the other way: **the Blue-Yellow variants are not
general-purpose colourblind themes.** They deliberately leave red and green
close together, because tritanopia does not affect that axis. If you have
red-green deficiency, a Blue-Yellow variant will be worse for you than the
default.

## Install

```bash
omarchy theme install https://github.com/AlanRoman117/omarchy-beacon-dark-theme.git
omarchy theme set beacon-dark
```

Each theme lives in its own repository so that `omarchy theme install` works
directly. This repo is the source they are generated from; the published repos
are subtree splits of `themes/`.

To try a variant from a local checkout without publishing:

```bash
ln -s "$PWD/themes/omarchy-beacon-dark-theme" \
      ~/.config/omarchy/themes/omarchy-beacon-dark-theme
omarchy theme set omarchy-beacon-dark-theme
```

Omarchy treats a plain directory or a symlink to a working copy as your own
theme and stages it in full, so this gives you an edit-and-reload loop. Note
that it also skips the filtering a cloned theme goes through, so it will not
catch a file that would be dropped on a real install.

## How these were built

The hard problem is not hitting 7:1. It is hitting 7:1 **and** keeping six
colours apart from each other, because those two goals fight. Compressing a
palette toward one end of the lightness axis is what raises contrast, and it is
also what makes hues collapse into each other. A greyscale theme passes AAA
perfectly and is useless.

So the generator works in three stages:

1. **Hues are chosen for the target vision type.** The defaults use a full
   spread. The red-green variants use Okabe-Ito style substitutions: red
   becomes vermilion (hue 38 rather than 25), green becomes bluish-green (hue
   172 rather than 150). Those survive the protan and deutan confusion axes
   where crimson and grass green do not.

2. **Lightness is assigned by brute-force search.** A fixed ladder of contrast
   targets is distributed across the six hues by trying all 720 permutations
   and keeping the one that maximises the minimum perceptual distance between
   the pairs that carry meaning, under simulation. Lightness is the only
   channel a dichromat keeps, so **the contrast ladder is the separation
   mechanism**, not a side effect of it.

3. **Each colour's Oklch lightness is solved by binary search** so it lands on
   its contrast target exactly. Compliance is true by construction rather than
   by inspection.

Two constraints stop the result degenerating:

- A **chroma floor** rejects any assignment that pushes a slot so far up or
  down the lightness axis that its chroma gets gamut-crushed. This is what
  stops "green" resolving to white on a dark background and "cyan" resolving to
  black on a light one.
- A **plausibility rule**: yellow is never the darkest thing on screen and red
  is never the palest, in either mode.

### Priority pairs

Not all fifteen colour pairs matter equally. These five are held to a higher
bar, because confusing them costs you something real:

| Pair | Where it bites |
|---|---|
| red / green | `git diff`, test pass-fail |
| red / yellow | error vs warning |
| green / cyan | addition vs info |
| red / blue | error vs info |
| yellow / green | warning vs pass |

### Why WCAG 2.x is not the only check

WCAG 2.x relative-luminance contrast systematically overstates contrast when
both colours are dark, so a dark pair can pass 7:1 on paper and still be hard
to read. Every dark variant is therefore cross-checked with **APCA**, the
polarity-aware algorithm from the WCAG 3 work, and the Lc values are published
alongside the ratios.

## What is deliberately not AAA

Three places, documented rather than fudged.

**The selection band.** Selected text holds AAA against the selection
background. The band's own edge contrast against the desktop lands around
2.5:1, below the 3:1 WCAG 1.4.11 asks of a UI component. These pull in opposite
directions and no value satisfies both: lightening the band to clear 3:1
against a near-black desktop drops the selected text below 7:1. Legible
selected text won.

**Light-mode chromatic colours are dark jewel tones.** To clear 7:1 against a
near-white background, a colour has to sit below about 9% relative luminance.
There is no bright, cheerful, AAA-compliant orange on white. The light variants
look like ink on paper because that is what the arithmetic permits. If you want
brighter light-mode colours, the honest move is to target AA and say so. The
light variants' `orange` shows this most: it lands as a dark brown.

**Highlighted text in VS Code is AA, not AAA.** Selection, find matches and
diff highlights have to move toward the text colour to be visible. Each one is
solved so every syntax colour still reads at 4.5:1 or better on top of it,
which leaves the highlight at about 1.5:1 against the editor. Holding 7:1
would make the highlights invisible. Resting text everywhere in VS Code stays
at 7:1.

## Why protanopia and deuteranopia share a variant, and tritanopia does not

Protanopia and deuteranopia sit on nearly the same confusion axis, so one
well-designed red-green palette serves both. They are not identical, though:
protanopia comes with reduced luminance sensitivity to red, so reds look darker
and can approach black. The shared variant is tuned for that **protan worst
case**, which is why its red is a vermilion placed high on the contrast ladder
rather than a deep crimson. Anything that works for protan works for deutan;
the reverse is not reliably true.

Tritanopia is a different axis entirely and needs its own palette. Red and
green are trustworthy there, so the design work goes into separating blue from
green and yellow from magenta instead.

Every theme ships a `cvd-proof.png`: the same palette rendered four times,
under normal vision and all three simulations. Open the default dark proof and
the red-green dark proof side by side and the reason the variants exist is
immediately visible.

## Wallpapers

Each theme ships four flat papercut nature scenes in `backgrounds/`, with each
family set somewhere its colours already belong:

| Family | Setting |
|---|---|
| Beacon Dark | Night: alpine lake, pine ridge, a lighthouse headland, a meadow |
| Beacon Light | Morning: dunes, a birch grove in snow, shoreline stones, a distant range |
| Red-Green | Ocean and desert, in blue and orange, the colours that stay vivid for red-green colour vision deficiency |
| Blue-Yellow | Forest, flowers and a volcano, in greens and warm reds, with no blue sky |

A wallpaper is not decoration here: the lock screen and bar draw directly onto
it. Landforms sit low in the frame or in the corners, leaving open sky across
the centre. The scenes are papercut rather than photographs because realistic
grass, leaves, stars and water are exactly the fine repeating detail rule 2
below forbids. Each `backgrounds/README.md` carries a generation prompt for
adding more.

Three rules every wallpaper is checked against:

1. **Keep the centre clear.** The lock screen draws in the middle of the frame.
   On dark themes nothing in the central third rises above 20% luminance; on
   light themes nothing falls below 50%.
2. **No high-frequency detail.** Flat colour and hard edges only. Fine stripes,
   dot grids and dense noise cause visual stress, and they shimmer through the
   bar's translucency.
3. **Match the palette's hue policy.**

| Variant | Allowed | Forbidden |
|---|---|---|
| Dark / Light | any, low saturation | — |
| Red-Green | blue, sky blue, navy, orange, amber | green, red, magenta |
| Blue-Yellow | vermilion, green, magenta, amber, cream | blue, teal, cyan |

A red-green contrast in a wallpaper is invisible to exactly the people the
red-green variant is for, and the same logic applies to blue and teal in the
blue-yellow variants.

`tools/check-wallpaper.py` audits a set of images: it runs both the Machado
(2009) and Viénot/Brettel/Mollon (1999) models, flags colours the two models
disagree about, and measures how much of the frame will fight overlaid text.
One known limitation: its worst-block contrast check scans the whole frame
rather than just the centre, so it fails images whose shapes sit harmlessly in
a corner. Treat that line as advisory and check the central third by eye.

A finding worth passing on: when testing candidate wallpapers through Chromium
DevTools' vision deficiency emulation, **reduced contrast was harsher than any
of the colour-blindness filters**. It simulates low vision and poor displays,
which affect far more people than tritanopia does. Check against it.

### Other apps Omarchy themes

Omarchy generates themes for btop, Helix, Obsidian, Pi, Claude Code, T3 Code,
Hermes and the screen share picker from `colors.toml`. Those templates assume a
stock palette, and nothing checked them against Beacon's guarantees. On every
Beacon variant, six of the eight failed at least one pair. btop's selected
process row, for example, drew the accent on the selection band at 3.41–4.66:1.

`tools/apps.py` renders each template exactly as Omarchy does (a parity check
byte-compares the result with Omarchy's own output), measures the text,
selection and border pairs, and ships a patched copy only for apps that fail.
Patches change one to three values each and reuse colours already verified
elsewhere: the palette, or the VS Code theme's selection and hover surfaces.
Helix and the share picker pass as generated, so Beacon ships nothing for them.
The full before-and-after table is in [`APPS-REPORT.md`](APPS-REPORT.md).

Terminals and Neovim need no patch: they draw the verified ANSI colours, and a
theme installed from git cannot ship `.lua` or terminal config files anyway.

### VS Code

Omarchy themes VS Code in one of two ways. A stock theme names a marketplace
theme, and Omarchy installs it. A theme installed from git is not allowed to
name one, because installing an extension runs code, so Omarchy falls back to a
generic template filled from `colors.toml`. That template assumes a palette
shaped like the stock themes. With Beacon's AAA-level `muted` it paints bright
grey panels and leaves secondary buttons at under 2:1.

So each theme ships its own `vscode-theme.json`. It is colour-only JSON, it
survives the install filter, and Omarchy never overwrites a file the theme
already provides. Omarchy applies it as the theme called "Omarchy".

**Reload VS Code after switching to a Beacon theme:** run
**Developer: Reload Window** from the command palette, or restart VS Code. Omarchy registers every
theme that has no marketplace theme under the same VS Code name, "Omarchy",
and only swaps the colour file behind it (`omarchy-theme-set-vscode`). The
`workbench.colorTheme` setting therefore does not change, so VS Code keeps the
colours it already loaded. Stock themes such as Osaka Jade switch live because
their VS Code theme names differ. This affects every Omarchy theme installed
from git, not only Beacon, and a theme cannot fix it from its own files.

It is generated from the same palette objects as `colors.toml`, and
`tools/verify.py` checks around 70 text and indicator pairs per variant. It
refuses to write any theme where one fails. Resting surfaces step away from the
text (darker on dark themes, lighter on light ones), so nothing verified
against the editor loses contrast in the side bar or a hover widget.

Each palette also carries an `orange`. Omarchy's app templates expect one and
substitute yellow when it is missing, which merged numbers with types in VS
Code. It is solved after the six-slot optimisation, so the six verified colours
do not move.

On the Red-Green variants, diff highlights for inserted and removed lines are
equally light and differ by hue alone. Read VS Code's `+`/`-` gutter markers
and the solid gutter bars there. The bars use the palette's red and green, which
are separated in lightness.

The `shell.*.toml` files are **section overrides**, not a replacement
`shell.toml`. Omarchy generates the full file from its own template and each of
these replaces one section. Shipping a whole hand-written `shell.toml` would
silently miss any key a future Omarchy release adds.

Border alphas are pinned to `1.0` throughout. Translucency quietly eats the 3:1
WCAG 1.4.11 requires of a control boundary, and a focus ring at 60% alpha is
not a focus ring that meets 2.4.13.

## Two things a theme cannot do for you

**Window border width.** The palette sets the active border colour and
guarantees it clears 3:1 against the desktop. Width lives in Hyprland config.

**Reduced motion.** WCAG 2.3.3 is about animation, which no palette controls.

```
# ~/.config/hypr/hyprland.conf
general    { border_size = 3 }
animations { enabled = false }
```

Both are user config on purpose: a theme cloned from a git URL has its
`hyprland.lua` stripped before staging, so a theme genuinely cannot set them.

## Repository layout

```
omarchy-beacon-theme-family/
├── themes/
│   ├── omarchy-beacon-dark-theme/          # each published as its own repo
│   ├── omarchy-beacon-light-theme/
│   ├── omarchy-beacon-redgreen-dark-theme/
│   ├── omarchy-beacon-redgreen-light-theme/
│   ├── omarchy-beacon-blueyellow-dark-theme/
│   └── omarchy-beacon-blueyellow-light-theme/
├── tools/
│   ├── colorlib.py          # Oklch, WCAG, APCA, CVD simulation
│   ├── verify.py            # generates palettes, VS Code themes + CONTRAST-REPORT.md
│   ├── vscode.py            # builds and checks each vscode-theme.json
│   ├── apps.py              # verifies and patches Omarchy's generated app themes
│   ├── assets.py            # generates shell overrides + background prompts
│   ├── theme_readmes.py     # generates each theme's README from its palette
│   ├── preview.py           # generates palette.png + cvd-proof.png
│   └── check-wallpaper.py   # wallpaper CVD + luminance audit
├── publish.sh               # subtree-splits themes/ into the six repos
└── CONTRAST-REPORT.md
```

Themes are authored here and published outward. Editing a palette means editing
`tools/verify.py` and re-running it, not hand-editing a `colors.toml` — the
per-theme READMEs are generated from the palettes too, so the published numbers
cannot drift from the colours.

## Verifying

```bash
python3 tools/verify.py         # palettes + VS Code themes + CONTRAST-REPORT.md
python3 tools/assets.py         # shell overrides + background prompts
python3 tools/theme_readmes.py  # per-theme READMEs
python3 tools/preview.py        # palette.png + cvd-proof.png
python3 tools/check-wallpaper.py --mode dark  themes/*/backgrounds/*-dark-*.jpg
python3 tools/check-wallpaper.py --mode light themes/*/backgrounds/*-light-*.jpg
```

No third-party dependencies for the colour maths. `preview.py` and
`check-wallpaper.py` need Pillow (`sudo pacman -S python-pillow`) and nothing
else.

Verify by eye as well. Open `cvd-proof.png`, and check every palette in plain
greyscale — the fastest way to confirm that lightness alone carries enough of
the signal.
